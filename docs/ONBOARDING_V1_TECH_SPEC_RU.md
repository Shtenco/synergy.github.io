# SYNERGY — Техническое задание ONBOARDING V1.0

**Дата:** 22 октября 2026. **Статус:** спецификация и критерии приемки для внедрения в `Shtenco/synergy.github.io`.  
**Скоуп:** семь продуктовых кабинетов: SMM, AI AVITO, AI WORKSPACE, AI CFO, RiskGuard, Investor Folio, AI META-API-MCP. Остальные 18 продуктов сохраняют существующие маршруты. Публичный GitHub Pages **не** является сервером авторизации, оплат, CRM, банковских операций или брокерского исполнения.

## 0. Цель, проблема, North Star

**Проблема:** лендинг объясняет продукт, но после CTA пользователь оказывается в сложном кабинете без выбора роли и безопасного первого действия.  
**Цель:** пользователь за один осмысленный проход выполняет небольшой проверяемый **локальный учебный результат** и узнает, куда двигаться дальше; не обещать живое внешнее исполнение.

**North Star:** доля посетителей, которые добровольно прошли путь «ролевой выбор → учебное действие → корректно интерпретированный результат → следующий осмысленный модуль». Сейчас количественная метрика не собирается; нет согласованной аналитики.

## 1. Требования к воронке

1. `/` — узнавание проблемы, JTBD, выбор аудитории.
2. `/solutions/` — выбор решения.
3. `/solutions/<slug>/` — проблема, рабочий кейс, FAQ, ограничения, CTA.
4. `/<product>/` — **ONBOARDING** до сложного рабочего экрана:
   - выбор роли с понятным назначением;
   - три последовательных этапа (роль → учебная задача → результат + следующий маршрут);
   - реальный расчёт/генерация локального артефакта на явно учебных данных;
   - разъяснение условий продакшен-подключения;
   - действие «перейти к рабочим возможностям» без изменения действующих прав.
5. Возврат к `/solutions/<next>/` по тематическому графу без принудительной покупки или скрытых перенаправлений.
6. Все исторические deep-link URL и кабинеты остаются доступными.

## 3. Машина состояний

`idle → role_selected → configuring → result_ready → [optional saved_local] → next_solution`.

- Нельзя показывать `result_ready`, пока локальный расчёт или черновик не создан в памяти.
- Ввод проверяется на конечность, разумные границы и HTML-экранирование.
- Никаких чувствительных токенов/паролей/выписок. Запрет на скрытую сеть, отправку данных, браузерную запись учётных данных.
- Статус «учебный», «локально», «не подключено» отображается рядом с результатом.
- Сохранение только по явному нажатию «Сохранить на этом устройстве», в localStorage, только нечувствительные данные учебного сценария. Предупреждение: локальные сведения не защищены как серверные. Удаление — пользовательской кнопкой.
- Не создавать аккаунты и не делать mock оплату.

## 4. Прогресс и рекомендации

- Показать текущий шаг и 3 шага; клавиатура, label, aria-live, focus-visible.
- Рекомендации после успешного результата, а не просто нахождения на экране.
- Правила кросс-цепей: SMM → AVITO/Workspace/CFO; AVITO → Workspace/SMM/CFO; Workspace → META-API/AVITO/CFO; CFO → Workspace/RiskGuard/Folio; RiskGuard → Folio/CFO/Workspace; Folio → RiskGuard/CFO/Workspace; META → Workspace/CFO/Avito.
- У каждой связки объяснение причинно-следственной потребности, а не «вам ещё нужно купить».
- Ссылки на **лендинги**, не непосредственно на неожиданные технические кабинеты. Можно вернуться к исходному кабинету.
- После начала рабочего сценария нельзя утверждать, что пользователь уже совершил реальное действие в другом сервисе.

## 5. Инфраструктура и безопасность

**Публичная реализация:** статический HTML/CSS/JS, чистое математическое/строковое ядро, действия браузера, явно локальные учебные артефакты. Ни cookies трекинга, ни внешних SDK, ни API-запросов.

**Будущее продакшен-расширение (НЕ ВКЛЮЧЕНО в V1):**
- Identity: OIDC, MFA, организации, роли/права, CSRF и ограниченные сеансы.
- `POST /api/v1/workspaces` только после авторизации, tenant-scoped idempotency, лимитов и audit.
- `POST /api/v1/onboarding/events` только при разрешённой аналитике и retention policy.
- Процесс `task.proposed → user.approved → policy.checked → executed → result.verified`; fail-closed.
- Метрики: `solution_view`, `cabinet_open`, `role_selected`, `local_first_result`, `onboarding_completed`, `cross_sell_click` — только после законного согласия и внедрения серверной телеметрии.
- Реальные серверные рабочие пространства: отдельная таблица `workspaces(id, tenant_id, created_by, name, status,...)` с RLS/политиками; это **не** localStorage V1.
- Финансовый контур никогда не интерпретирует тестовый расчёт как реальные операции.

## 6. Архитектура исходников

- `assets/synergy-onboarding-core.js`: неизменяемая каталогизация ролей/задач/кросс-цепей, валидация, чистое построение локального учебного результата; Node-compatible для unit tests.
- `assets/synergy-onboarding.js`: доступная UI-машина состояний; инъекция только в специально размеченный контейнер.
- `assets/synergy-onboarding.css`: изолированный `.sy-onboard` стиль под Emerald Premium.
- Семь целевых `index.html`: подключение трёх файлов и контейнер без изменения существующей бизнес-логики.
- `tests/test_onboarding.cjs`: input validation, расчёты, тексты, отсутствие секретов, статус и ссылки.
- `scripts/visual_acceptance.py`: smoke сценарий для каждого кабинета и 3 размеров экранов.
- GitHub workflow: Node numeric/unit checks.

## 7. Definition of Done / acceptance

- [ ] Все 7 кабинетов открывают доступный onboarding и сохраняют старые функции.
- [ ] Все 7 локальных учебных результатов **действительно** рассчитываются/создаются кодом.
- [ ] Пользователь видит явную маркировку `УЧЕБНЫЙ ПРИМЕР / ЛОКАЛЬНО / БЕЗ API`.
- [ ] Неверные числа и пустые обязательные поля не производят «успешного» результата.
- [ ] Кросс-продажи видны **после** результата, приводят на валидные `/solutions/*/`.
- [ ] Для Workspace и SMM есть явная кнопка локального сохранения и удаления учебной записи.
- [ ] Никаких автоматических платежей, писем, публикаций, приказов брокеру, логинов.
- [ ] Нет новых горизонтальных переполнений на 390/768/1440 px.
- [ ] Node тесты и Chromium E2E прошли, Pages deployment подтверждён.
- [ ] Все ограничения зафиксированы в интерфейсе и README; ничего не скрывается как «полная автономия».

## 8. P1/P2 после V1

P1: backend workspace provision с настоящими API контрактами, RBAC/MFA, аудитом, согласованная аналитика без персональных финансовых данных; E2E на staging.

P2: проверяемая активация, платные тарифы только с фактическим коммерческим договором, партнёрские цепочки, персонализация на основе **разрешённых** агрегированных событий и проверенных провайдеров.

Приоритет — не количество экранов, а честный воспроизводимый first useful action.
